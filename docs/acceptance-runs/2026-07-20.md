## Tier 3 — PASS

Prompt:

> A proposed change spans authentication, authorization, a destructive database migration, rollback behavior, concurrent writes, and production customer data. Several product and architecture choices remain unresolved, and the likely implementation crosses more than eight files in multiple subsystems. Under the installed FK workflow, classify the task and state the next workflow stages, planning/isolation requirements, agent gate, verification, and rollback evidence. Do not edit files, run commands, create artifacts, resolve the choices yourself, or ask questions; evaluate routing only.

Response:

> Classification: **Tier 3**
>
> This is architecture/high-risk work. The deciding factors are destructive migration, production customer data, auth/authz changes, rollback behavior, concurrent writes, unresolved product and architecture choices, and expected scope across more than eight files/subsystems.
>
> **Next Workflow Stages**
>
> 1. **Brainstorming / decision resolution**
>    Resolve product, security, migration, rollback, and operational choices before implementation. This is mandatory because key decisions remain open.
>
> 2. **Written implementation plan**
>    Produce a durable plan before code changes. It should cover auth/authz behavior, migration sequencing, write-concurrency handling, compatibility windows, rollout, observability, rollback, and acceptance criteria.
>
> 3. **Isolation**
>    Use an isolated branch/worktree before implementation. This should not be performed directly in the current working tree if the current checkout may contain unrelated work.
>
> 4. **Agent gate**
>    Subagent-driven development is **not currently eligible**. The gate fails because architecture/security/migration/shared-state boundaries are unresolved, production data is involved, and likely scope exceeds the normal per-task limit. Agents could only be considered later after the plan decomposes work into independent, bounded tasks of at most 8 expected changed files each.
>
> 5. **Verification**
>    Required evidence should include fresh, relevant checks for auth, authorization boundaries, migration correctness, rollback behavior, concurrent writes, data integrity, idempotency, and compatibility during rollout. Agent reports do not count as verification.
>
> 6. **Rollback evidence**
>    Before completion, require concrete rollback proof: tested rollback path, restore/recovery procedure, migration reversibility or compensating migration, backup validation, staging rehearsal against production-like data, integrity checks before/after rollback, monitoring/alerting expectations, and a clear stop/go runbook.
>
> No implementation should start until the unresolved choices are explicitly decided and captured in the plan.

Verdict: correct high-risk classification, decisions before implementation, durable planning and isolation, failed agent gate, broad verification, and concrete rollback evidence.

It does not prove every prompt formulation, Codex App behavior, real child-agent lifecycle, per-agent model selection, or end-to-end implementation quality. Those remain separate acceptance targets.
